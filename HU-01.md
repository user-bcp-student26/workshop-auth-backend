## Contexto
El flujo de login actual entrega un token generado por una utilidad legacy que codifica datos en Base64 y contiene un secreto fijo en codigo. Este enfoque no garantiza integridad del emisor ni permite una gestion segura del secreto por entorno.

## Ajustes necesarios
- Reemplazar el token reversible por un token firmado criptograficamente.
- Eliminar el secreto embebido en codigo y cargarlo desde configuracion por entorno.
- Definir politica de expiracion y validacion del token (firma, expiracion y formato invalido).
- Mantener el contrato HTTP existente de login y ajustar solo la construccion y validacion del token.

## Criterios de aceptacion
- Prueba unitaria de token firmado: dado un login valido, el token emitido debe pasar verificacion de firma con la clave configurada.
- Prueba negativa de integridad: al alterar un byte del token, la verificacion debe fallar.
- Prueba de expiracion: un token vencido debe ser rechazado por el validador.
- Prueba de configuracion: si falta la clave de firma en configuracion, el componente de token debe fallar de forma controlada sin exponer secretos.
- Prueba de compatibilidad de API: login exitoso mantiene respuesta 200 con los campos esperados del contrato actual.

## Evidencia esperada
